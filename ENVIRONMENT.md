# Переменные окружения

Единственный редактируемый источник значений — `.env` в корне репозитория. `.env.example` описывает все параметры без настоящих секретов. Локальные значения из старых файлов перенесены в `.env`, старые файлы удалены. Удалите ссылки на них из настроек запуска IDE.

Для нового клона: `Copy-Item .env.example .env`. Заполните доступ к S3 и JWT. В существующем рабочем каталоге не перезаписывайте `.env` шаблоном.

## Docker

Запускайте команды из корня репозитория:

```powershell
docker compose config --quiet
docker compose up -d
```

Compose читает `.env` и через `environment` передаёт каждому контейнеру только нужные параметры. Java не читает `.env` напрямую в Docker. Внутренний HTTP-порт каждого приложения — 8080; внешние порты задаются в `.env`.

Dockerfile копирует уже собранный JAR: перед запуском приложений требуется успешная Gradle-сборка. Инфраструктуру можно запустить отдельно:

```powershell
docker compose up -d kafka postgres-user-db postgres-upload-db kafka-ui cloudbeaver
```

## IDE и Gradle

В IntelliJ задайте рабочую директорию корнем репозитория и активный Spring-профиль `local` (`SPRING_PROFILES_ACTIVE=local`). Профиль загружает корневой `.env` как properties, выбирает внешний порт сервиса и подключается к опубликованным портам PostgreSQL и Kafka.

Если рабочая директория другая, передайте `PIPELINE_ENV_FILE` с абсолютным путём к `.env` (для Windows удобно использовать `/`).

Пример из корня репозитория:

```powershell
.\gradlew.bat :upload-service:bootRun --args=--spring.profiles.active=local
```

Не запускайте одновременно контейнер и IDE-экземпляр одного приложения на одном внешнем порту. Для работы с S3 из IDE укажите достижимый с хоста `AWS_ENDPOINT`; для локального S3 это обычно `http://localhost:9000`. S3 в этом Compose не развёрнут.

## Какие параметры менять

| Параметры | Назначение |
| --- | --- |
| `API_GATEWAY_PORT`, `*_SERVICE_PORT` | Внешние HTTP-порты и порты приложений в профиле local |
| `POSTGRES_USER_PORT`, `POSTGRES_UPLOAD_PORT` | Внешние порты двух БД |
| `USER_DB_*`, `UPLOAD_DB_*` | Имя базы, пользователь и пароль; одно значение получают и БД, и приложение |
| `JWT_SECRET_KEY`, `JWT_EXPIRATION_MS` | Общие параметры JWT |
| `AWS_*` | Общие настройки S3 и названия двух бакетов |
| `KAFKA_PORT`, `KAFKA_EXTERNAL_HOST` | Внешний адрес Kafka для клиентов из IDE |
| `KAFKA_*_TOPIC_NAME` | Общие имена топиков у отправителей и получателей |
| `KAFKA_*_GROUP_ID` | Отдельная consumer group каждого приложения |
| `KAFKA_TOPIC_*` | Параметры создаваемых приложениями топиков; по умолчанию один брокер, одна реплика |
| `AI_SERVICE_URL` | Адрес отдельно развёрнутого AI-сервиса |

В Docker клиенты Kafka всегда используют `kafka:9092`, PostgreSQL доступен по имени соответствующего Compose-сервиса и порту 5432. Эти адреса задаёт Compose. В IDE профиль local использует внешние адреса. Параметры самого брокера не передаются Java-сервисам или Kafka UI.

`USER_DB_HOST`, `USER_DB_PORT`, `UPLOAD_DB_HOST`, `UPLOAD_DB_PORT`, `KAFKA_BOOTSTRAP_SERVERS`, `SERVER_PORT` и URL downstream-сервисов — параметры запуска, которые устанавливает Compose; при нестандартном запуске их можно переопределить окружением процесса. Переменные оболочки имеют приоритет над `.env` при подстановках Compose. Удалите старые переменные из Run Configuration, если они перекрывают новые настройки.

`.env` должен содержать простые строки `KEY=value` без кавычек, подстановок `${...}` и shell-команд: файл используется и Compose, и Spring как properties. Для секретов избегайте обратных слешей либо учитывайте правила экранирования Java properties.

Изменение учётных данных PostgreSQL в `.env` не меняет пользователей уже инициализированной базы на существующем volume. Сначала согласуйте их с реальной БД; удалять volumes для применения конфигурации не требуется. Параметры существующих Kafka-топиков также не меняются автоматически при изменении defaults.

`docker compose config --quiet` проверяет конфигурацию без печати секретов. Полный `docker compose config` выводит подставленные значения, включая пароли.
